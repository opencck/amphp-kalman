# ADR-001 — Раскладка матриц в памяти: плоский row-major `array<int, float>`

Дата: 2026-09-11. Статус: принято.

## Контекст

Исходный проектный документ (ныне [BRIEF](../../BRIEF.md) §3) требует замерить
варианты хранения матриц до написания ядра.
Ядро фильтра — плотные циклы по float; узкое место — интерпретатор PHP,
а не арифметика (§6.1). Замер: `bench/LayoutBench.php`, ядро `P ← F·P·Fᵀ`
(две тройные петли, верхний треугольник с зеркалированием).

Окружение: PHP 8.3.33 NTS x64 (Windows 11), `opcache.enable_cli=1`,
`opcache.jit=1255`, `opcache.jit_buffer_size=128M`, `zend.assertions=-1`,
Xdebug не загружен. Лучшее из 5 повторов.

## Результаты (мкс на одну операцию `F·P·Fᵀ`)

| n | flat row-major | nested `array[][]` | `SplFixedArray` | flat / nested | flat / SplFixed |
|---|---:|---:|---:|---:|---:|
| 2 | 0.098 | 0.154 | 0.421 | **1.57×** | 4.3× |
| 4 | 0.591 | 0.694 | 2.772 | **1.17×** | 4.7× |
| 8 | 3.895 | 4.191 | 17.979 | 1.08× | 4.6× |
| 16 | 29.0 | 28.2 | 131.2 | 0.97× | 4.5× |
| 32 | 221.7 | 217.9 | 988.8 | 0.98× | 4.5× |
| 64 | 1699 | 1713 | 7722 | 1.01× | 4.5× |

Наблюдения:

- Под JIT плоский и вложенный массивы сходятся при n ≥ 8: JIT убирает
  hash-lookup вложенности, остаётся арифметика индексов. При n ≤ 4 (LLT, пара,
  бета — самые частые размеры в финансах) плоский массив быстрее на 17–57 %.
- `SplFixedArray` стабильно в 4.5× медленнее: каждый доступ — вызов метода
  `offsetGet/offsetSet`, JIT его не инлайнит. Он остаётся только для больших
  траекторий сглаживателя (§2.12), где важна память, не скорость.
- Плоский массив — единственный вариант, который позволяет представить
  `phi = P·hᵀ` как один проход по строке, хранить `U` из UD-формы и `S` из
  SRKF тем же типом и передавать матрицы в воркер без преобразований.

## Решение

- Все матрицы — плоские `array<int, float>` row-major: `M[i][j]` → `$M[$i * $n + $j]`.
  Вложенные массивы запрещены в `Domain\Linalg`, `Domain\Covariance`, `Domain\Filter`
  как параметры и возвращаемые значения (`ArchitectureTest::testNoNestedArraysInHotCore`);
  конвертер для границы API — `Domain\Linalg\Nested`.
- Симметричные матрицы хранятся полностью (не packed): доступ `P[i*n+j]` дешевле
  вычисления индекса треугольной раскладки, а строки и столбцы читаются одинаково.
- Буферы создаются `array_fill(0, n*n, 0.0)` один раз в конструкторе и никогда
  не `unset` — массив остаётся packed без хеширования.
- В горячих методах массивы-свойства берутся по ссылке (`$P = &$this->P`),
  размеры — в локальные переменные до цикла, внутри цикла нет вызовов функций.
- phpdoc-тип `array<int, float>` (не `list<float>`): phpstan не умеет доказать
  «список» после записи по вычисляемому индексу, а код при этом корректен.

## Первые цифры шага фильтра (`bench/FormBench.php`, то же окружение)

| Форма | LLT n=2 m=1 | n=4 m=2 | n=8 m=4 | n=16 m=8 | n=32 m=16 |
|---|---:|---:|---:|---:|---:|
| Sequential | 0.85 мкс | 2.44 | 9.4 | 55.5 | 375 |
| Joseph | 0.92 | 2.58 | 10.2 | 59.8 | 406 |
| UD | 1.57 | 3.85 | 15.9 | 96.5 | 695 |
| SquareRoot | 1.72 | 4.11 | 17.2 | 104 | 736 |
| Цель §1.3 (Sequential / UD) | ≤ 3 / ≤ 5 | ≤ 3 / ≤ 5 | ≤ 12 / ≤ 20 | ≤ 60 / ≤ 100 | ≤ 300 / ≤ 500 |

n = 4…16 — в пределах целей уже в фазе 2. n = 32 с **плотной** F (O(n³) predict)
на 25–40 % медленнее цели; цель §1.3 сформулирована для разреженной F
(ETF-корзина, O(n²) predict) — проверяется в фазе 8. Аллокаций на шаг — 0 байт
для всех форм (`bench/AllocBench.php`).

## Последствия

- `KernelBench` (фаза 3) проверит, дают ли развёрнутые ядра `Dim2/Dim4`
  дополнительные 2–3× поверх плоского массива.
- FFI/OpenBLAS (фаза 8) имеет смысл только при n ≥ 32, где плотный predict
  превышает цель.
